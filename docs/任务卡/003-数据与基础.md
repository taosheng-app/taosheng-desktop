# 任务卡 003：数据与基础（波次 2）

## 目标

把安卓版的数据库层完整搬到 `core`：`CaptureDatabase`（Room，**DB 版本 33**）及其全部实体、DAO、迁移、FTS4 搜索索引，加上被它依赖的几个小而底层的包（`usage`、`prompts`、`privacy`、`diagnostics`、`onboarding`、`context` 的契约与本地实现）。

**核心约束：表结构与安卓逐字一致。** 这样桌面版才能读取安卓备份（见 plan 的已确认决定 4），迁移路径也与安卓完全相同。这一波之后，后面所有业务包都能直接依赖 `CaptureDatabase`。

总计划见 `plan.md`；上一张卡见 `docs/任务卡/002-交付说明.md`（`KeyValueStore`/`SecretStore`/`Scheduler`/`Notifier`/`AppDirs` 的迁移对照表）。安卓原项目在 `D:\projects\github\TaoSheng`（只读）。

## 调研结论

- 实体/DAO 分布在 **20 个文件、约 2700 行**：`data/` 下 9 个，另有 `devices`、`envsound`、`importer`、`location`、`push`、`redo`、`skills`、`things`、`topic`、`search` 各一两个。**39 个实体**（含 3 个 FTS4），**19 个 DAO**，其中 **9 个是抽象类**（带函数体的事务方法）。
- 特性：`@Relation`/`@Embedded` 各 4 处、`@Transaction` 60 处、`@RawQuery` 1 处（`ReviewDao.materialChanges`）。
- **已在本卡调研时用最小库验证（Room 2.8.5 + KSP 2.3.13）**：抽象类 DAO、`@Transaction` 带函数体、`@Embedded`+`@Relation`、Flow 返回值**均可用**；**`@RawQuery(SupportSQLiteQuery)` 不可用**（`androidx.sqlite.db` 是 Android 专属包），需要改写（见下）。
- 迁移 `MIGRATION_1_2`…`MIGRATION_32_33` 共 32 个，全部是 `db.execSQL(...)`；其中 4 个会调用辅助安装函数（`SearchIndex.install`、`ImportRecordSchema.install`、`LocationSchema.create`/`PlaceSchema.create`/`addManual`）。数据库回调 4 个（`SearchIndex`、`ImportRecordSchema`、`ThingSchema`、`PendingDigestSchema`），`onCreate`/`onOpen` 时安装触发器。
- Android 专属依赖集中在：`SupportSQLiteDatabase`（迁移与回调）、`SimpleSQLiteQuery`（裸查询）、`Context`（`CaptureDatabase.open`）、以及 `location` 包里的 `LocationManager`/`Geocoder`/`ContextCompat`。
- 数据层引用了少量其他包的类型：`topic.OUTSIDE_TOPICS`、`usage.UsagePurpose`、`search.Vectors`、`capture.VoiceInputDedup`、`ask.AskConversation`、`skills.SkillCardRow` 等，需要一起搬或前置。

## 约定

- 包名保持 `app.resound.*`，放 `core/src/desktopMain`（Room 的 KSP 只对 `kspDesktop` 配置）；纯中立的契约接口（`*Contract.kt`）放 `commonMain`。
- 保持 **`CaptureDatabase.VERSION = 33`** 和 `MIGRATIONS` 清单的写法；新增迁移只在 `CaptureDatabase.MIGRATIONS` 加一条。迁移测试用 `CaptureDatabase.VERSION`，不写死数字（沿用 AGENTS.md 的教训）。
- 实体、DAO、表名、列名、索引、外键、默认值**一字不改**。允许的修改只有：包引用的调整、`SupportSQLiteDatabase`→`SQLiteConnection`、`Context`→`AppDirs`、删除 Android 专属成员。
- 不修改 `*Contract.kt` 的签名；确需修改在交付说明里写明。
- 事务封装按卡 001 定案：新增 `CaptureDatabase.inTransaction { }`（`useWriterConnection { it.immediateTransaction { } }`），安卓 `db.withTransaction` 全部改调它。
- schema 导出到 `core/schemas/app.resound.data.CaptureDatabase/33.json`，**并与安卓的 `33.json` 逐字节对比**，不一致要逐条解释。

## 要做的

### 1. 实体、DAO、关系类型

- 搬 20 个文件到对应包（`data`、`devices`、`envsound`、`importer`、`location`、`push`、`redo`、`skills`、`things`、`topic`、`search`），其中 `devices`、`push`、`skills`、`topic`、`things`、`importer`、`redo` 等业务包里**只搬数据文件**（实体/DAO/Schema 对象），业务逻辑留给波次 4～5，但被 DAO 引用的小类型一并搬。
- 抽象类 DAO 保持抽象类；`@Transaction open suspend fun` 保持。
- 删除 `location` 里的 `LocationManager`、`Geocoder`、`ContextCompat` 相关代码（`LocationRepository.create(context, ...)` 等），只保留实体、DAO 和 `LocationSchema`/`PlaceSchema`；定位本身是“先忽略”项。

### 2. `@RawQuery` 改写

- `ReviewDao.materialChanges(SupportSQLiteQuery): Flow<Int>` 只用来“订阅失效通知”，调用方永远传 `SELECT 1`（`RoomReviewRepository.kt:68`）。改为 `@Query("SELECT 1 FROM memory_events LIMIT 1")` 之类的**固定查询**，并保证 `memory_events`、`memory_items`、`embeddings` 任一表变化都触发 Flow 重新发射（Room KMP 按查询里引用的表观察失效，所以查询要**同时引用这三张表**，例如 `SELECT 1 WHERE EXISTS(...) OR EXISTS(...) OR EXISTS(...)` 的写法需要实测能否注册三张表的观察）。
- 若固定查询无法覆盖三张表，改用 `db.invalidationTracker.createFlow("memory_events", "memory_items", "embeddings")`。必须有一个测试证明任一表写入都会触发发射。

### 3. 迁移与回调

- `Migration` 改用 KMP 版 `Migration(start, end) { connection -> ... }`，`db.execSQL` → `connection.execSQL`；`MIGRATIONS` 清单保持 32 条。
- `SearchIndex.install`、`ImportRecordSchema.install`、`ThingSchema.create/install`、`PlaceSchema.create/addManual`、`LocationSchema.create`、`PendingDigestSchema.create/install` 入参改为 `SQLiteConnection`，SQL 不变；卡 001 已有的 `SpikeSearchIndex` 并入正式的 `SearchIndex`（含 `lines_fts`、`events_fts`、`items_fts` 三套与 embeddings 失效触发器，以及 `search_event_hidden`），删除 `Spike*` 验证类。
- 数据库回调：`onCreate` 与 `onOpen` 的安装逻辑保持原样（触发器 `IF NOT EXISTS`，重复执行无害）。

### 4. `CaptureDatabase.open`

- 签名改为 `open(file: File)` / `openInMemory()`，用 `BundledSQLiteDriver`，查询协程上下文 `Dispatchers.IO`，保持 `addMigrations(*MIGRATIONS)` 与四个回调。
- 数据库文件位置：`AppDirs.data("capture.db")`。**不开启 `fallbackToDestructiveMigration`**。

### 5. 小型基础包

按“契约 + 本地实现”整包迁移，去掉 Android 依赖：

| 包 | 内容 | 改动 |
|---|---|---|
| `usage` | `UsageContract`、`RoomUsageRepository`、`LlmBalance` | `Context`→注入；`LlmBalance` 里的网络与通知改用 `Notifier` |
| `prompts` | `PromptContract`、`LocalPromptTemplates` | 从 assets 读改为从 classpath 资源读；覆盖文件放 `AppDirs.data("prompts")` |
| `privacy` | `PrivacyContract`、`RoomPrivacyActions`、清理任务 | `PrivacyCleanupWorker` 改为 `Scheduler` 任务 |
| `diagnostics` | `CrashRecords`、`ProblemReportContract`、`LocalProblemReports`、LLM 诊断 | 崩溃钩子改 `Thread.setDefaultUncaughtExceptionHandler`，写到 `AppDirs.logs` |
| `onboarding` / `context` | 契约与本地实现 | `SharedPreferences`→`KeyValueStore` |
| 根包 | `AppName`、`OutputTime`（`PipelineProgress` 若无依赖一并搬） | 无 |

**资源文件**：把安卓 `assets/` 里的 `prompts/*.md`、`prompts/*.json`、`llm-providers.json` 拷进 `core/src/desktopMain/resources/`（原样，保留 MIT 声明在 NOTICE）。`silero_vad.onnx`、`homophones/*`、`skills/*`、`devices/*` 等留给用到它们的后续卡。

### 6. 安卓备份兼容（plan 已确认）

- 本卡只做**结构兼容测试**，不做备份恢复流程（那是波次 5 的 `backup`）：用安卓 `app/schemas/app.resound.data.CaptureDatabase/33.json` 作为期望结构，对比桌面生成的 `33.json`；再在测试里用桌面库建出完整库，逐表 `PRAGMA table_info` 与安卓 schema 的列名/类型/非空/默认值对照。

## 测试

按 AGENTS.md 的“适度”原则，关键路径 + 最易出错处：

- **迁移**（最重要）：造一个真实的 v1 库（用安卓 `1.json` 的建表语句）→ 逐版本迁到 33，Room 校验最终结构与 33 一致；迁移测试用 `CaptureDatabase.VERSION`、`CaptureDatabase.MIGRATIONS`。另加一条“从 v20 中间版本升级”和“重复打开不重复建触发器”。
- **结构对照**：桌面 `33.json` 与安卓 `33.json` 相同（或差异逐条说明）。
- **FTS4 三套索引**：中文/英文检索、插入/更新/删除触发器、事件“隐藏”触发器清除 embeddings。
- **关系与事务**：`SegmentWithLines`（`@Relation`）、带函数体的抽象 DAO 事务、回滚。
- **`materialChanges` 改写**：写 `memory_events` / `memory_items` / `embeddings` 任一表都触发 Flow。
- **外键级联**：删 `segments` 级联 `transcript_lines`、`memory_events` 级联 `memory_items`，且 FTS 与 `digest_pending` 的删除触发器同步。
- 小型基础包：每包 1～2 个（用量记账、提示词模板读取与覆盖、隐私清理、崩溃记录写入、开箱状态）。
- 搬运安卓对应的现有单元测试：`app/src/test` 下涉及上述包且不依赖 Robolectric/Context 的，原样搬；依赖 Robolectric 的改写为临时目录 + 内存库。**不要追求把 194 个测试全搬**，只搬与本卡包对应的关键用例，总量 5～15 个新增为宜。

## 不做

`backup`（备份恢复流程）、`capture`/`audio`/`transcribe` 等业务逻辑、各业务包的 Repository 实现（`RoomTranscriptRepository`、`RoomMemoryRepository` 等留给波次 4～5）、界面、定位实现、数据库加密。
